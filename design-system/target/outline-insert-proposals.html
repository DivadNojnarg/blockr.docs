Outline insert — adding blocks from the document

The outline already answers "what runs, in what order, described how". The open question: should it also add blocks, and where does the new block attach? The outline is a linear document view of a DAG, so insertion must state a rewiring rule — and it should only offer cases where that rule is unambiguous. Complicated surgery stays in the Workflow (dag).

The rewiring rule (all proposals share it)

Insert after block X:

X has no successor X -> [new] (pure append) X has exactly one, Y X -> [new] -> Y (spliced in) X has several: Y1, Y2 X -> [new] -> Y1, Y2 (all rewired onto new)

The three-successor case is the only judgement call: rewiring all successors keeps the document linear and matches "insert here" as read on the page. The alternative — attach the new block to one branch only — cannot be expressed by a position in a linear document at all, so it belongs in the dag view.

Insert before? recommend: no

Prepending is ambiguous in exactly the way appending is not: a block with several predecessors (a merge) has no single edge to splice into, and even with one predecessor "before X" is just "after X's predecessor" — the same action, reached from the other side. Offering both doubles the affordance for zero new capability. Every mock below therefore inserts after.

A — boundary insert rail recommended

A subtle ⊕ appears on every boundary between sections while the outline is hovered (the same geometry the reorder round's swap pill used). Clicking opens the block browser; the new block is spliced after the section above. The affordance sits exactly where the reader would point and says "something goes here" — the standard notebook / page-builder gesture.

B — chip append button

A small ⊕ on the chip (mirroring the drag grip on the opposite edge) meaning "append after this block". Ties the action to the block rather than to a gap, which reads more like the dag's "append block" action and is unambiguous about the anchor. But it competes with the grip for the same hover real estate, and boundaries — the place a reader thinks in — get no affordance.

C — end-of-chapter only

The most conservative reading: a persistent "+ Add block" affordance at the end of each chapter (and the document), nothing between sections. Zero hover chrome, obvious at a glance, and it keeps mid-pipeline surgery in the dag where the branch consequences are visible. Weakness: appending to a chapter whose last block has successors elsewhere still triggers the rewiring rule, so the simple look can hide the same complexity.

What the click opens

All variants open the existing block browser (the add-block sidebar), pre-scoped to blocks that accept the anchor's output. The mock shows a stub menu; the real thing reuses block_browser_ui() with an append_to() descriptor, exactly as the dock's append flow already does — so insertion is a thin call into machinery that exists.

Recommendation: A, insert-after only. The boundary is where a reader already points, one affordance covers both splice and append (the final gap), and it reuses the geometry the reorder round established. Keep "insert before" out: it adds a second affordance for an action already reachable, and it is undefined at merges. If mid-pipeline splicing ever proves confusing on branchy boards, C is the safe retreat — and the dag view remains the honest place for real graph surgery.

Decision record for blockr.outline. The rewiring rule is the load-bearing part: whatever variant wins, inserting after a block with several successors rewires all of them onto the new block, and anything finer belongs in the Workflow view.
