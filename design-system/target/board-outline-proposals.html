What the mock encodes

  • Stack = chapter. The stack's colored bar reappears as the chapter heading in the source (#' # Data prep), so the navigator's grouping and the report's sectioning are the same structure. Stacks finally do double duty: dashboard organisation and document outline.
  • Order rule. Both panes share one linearization: stacks ordered by their earliest block in dependency order, blocks in topo order within the stack. If a dependency forces a block out of its stack's span, it renders where the topo order puts it and its stack bar is shown split (not mocked here; rare in practice).
  • The switch is report inclusion, not dock visibility. In this surface the rail is the report's outline, so the one switch means "in the report". Flipping it off dims the code section to an include=FALSE stub and drops the prose; the group pill recounts. Dashboard visibility keeps living where it lives today (dock tabs, panel navigator proper).
  • Row ↔ section sync. Hover either side and the wire connects the pair; click jumps and flashes. This is the affordance that teaches "a block is a piece of code".
  • Code voice. The mock shows blockr.code-style idiomatic pipes rather than the pilot's local()/with() wrapping — the readable voice this view wants.
Where it would live: a widened "Code & report" sidebar (or a dock view of its own) built from two existing parts — the panel navigator's rail (feat/panel-navigator-dock, PR #253) and the pilot's live code pane (feat/block-docs-pilot). The sync layer (shared linearization + hover wire) is the only new machinery.

Mock only: three hard-coded blocks, hand-colored code, no real markdown or dockview. Decision record for the block-docs pilot spec; follows description-style-proposals.html (band = decided B).
