Measure switch — the one control a clinician sees

A locked CDEX view fixes everything about a chart except which measure is shown. Instead of exposing the chart block's mapping selectors (three selectors, every column in each), a small upstream measure switch block standardizes the chosen column(s) and the chart maps to the standardized output, fixed. The switch's single control is the whole viewer-facing UI. Running example: iris — pick Sepal Length or Sepal Width for the y-axis; x = Petal Length and color = Species never move. The switch always emits the long shape (measure + value), even for a single pick, so adding a second measure never changes the downstream schema. Choices display labels, never raw names (SYSBP → "Systolic Blood Pressure").

Baseline — what old CDEX does baseline

A select box in a sidebar, decoupled from the chart it drives. Works, but the control's scope is invisible (which outputs does it affect?) and it exists outside the workflow — nothing in the exported code shows where the choice entered the pipeline.

A — dropdown card for many choices

The switch block as a plain card: one labeled dropdown. This is the fallback that always works — a lab view offering thirty PARAMs cannot be a segmented control. Weakness for the 2–4 choice case: the alternatives are hidden behind a click, and a dropdown for two options feels heavier than the choice is.

B — segmented control recommended ≤ 4 choices

All choices visible, one click to switch, current pick unambiguous. This is the closest match to how clinicians actually use the old select box: flip back and forth while looking at the chart. The control type should be derived, not configured — ≤ 4 choices renders segmented, more falls back to the dropdown (A). No builder option needed.

C — multi-measure pills when multiple = TRUE

The builder allows picking several measures at once; the control becomes toggle pills and the chart facets by measure with free y scales (clinical measures rarely share units). Because the switch always emits measure + value, going from one facet to two is pure data — no chart reconfiguration. The last pill refuses to turn off: an empty selection would wedge the downstream chart, so ≥ 1 is validated in the control itself.

D — adopted into the consumer panel locked mode, later

In a locked board the switch is a separate DAG node, but giving it its own dock panel wastes a whole panel on one control. Proposal: when the board locks, an exposed switch collapses into the toolbar of the panel that consumes it. One panel, control and chart together — exactly the old CDEX experience, but the control is still a real block underneath (exported code shows the pivot; unlocking re-expands it to its own card). Needs dock support, so this is a follow-up, not v1: v1 locked mode simply shows the switch as its own slim card (A/B) docked above the chart.

Builder side — what the gear holds

Three settings, viewer sees none of them: which columns are offered (labels shown, stored as names), the default, and whether multiple picks are allowed. No "control type" option — segmented vs dropdown is derived from the choice count; pills are implied by multiple. Boolean follows the boolean-controls decision: multiple changes the UI mode, so it renders as a switch.

Ship the switch block with the control type derived from its config — segmented (B) for ≤ 4 single-pick choices, dropdown (A) beyond that, pills + facets (C) when multiple is on.
