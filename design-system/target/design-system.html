Target — the plan we are moving to

This is the proposed consolidation target for the blockr design system: one token layer and one set of component classes owned by blockr.ui. It documents today's reality (§1–4) only to justify where we are going (§5–6) — it is not a description of the shipped state. For the status quo — the primitives and component specs as currently implemented — see the markdown docs in design-system/.

blockr Design System

Current state, sources of truth, known drift — and the consolidation target: one token layer and one set of well-named component classes in blockr.ui that depending packages build on. Surveyed 2026-07-02 across blockr.dock, blockr.dplyr, blockr.ui, blockr.docs.

2.5 Control heights blockr.dplyr/dev/design-system.md:35-41 tokenize & reduce

The documented ladder is 42/38/30/26/24 — but the wild is worse: blockr.ui and blockr.dock both use 28px icon buttons (sidebar, block-browser add, dock header icons), dplyr adds a 22px expression link, so the same "small square icon button" exists at 22 / 26 / 28px across three packages. Proposal: three tokens.

Target ladder (live) — what folds into each tier
42px --blockr-control-h — standalone inputs & selects (absorbs the popover's 38px, single use)
30px --blockr-control-h-sm — nested in-row inputs, number inputs, add-row bar
26px --blockr-control-h-xs — compact: ALL icon buttons (22/26/28 → 26) and pills (24 → 26)

Demoted to component-internal detail (not ladder tiers): the 16px tag-remove hit-area inside Select tags, the 32px block-browser icon tile. Visible impact of the folds is mild — popover selects +4px, ui/dock icon buttons −2px, pills +2px. Fallback if pills should stay visually lighter than icon buttons: a 4th tier at 24px — but try 3 first; the 2px pill/icon distinction buys nothing.

2.6 Radii tokenize

Three tiers (live) — currently literal px scattered across all packages
8px lg — containers, inputs, dropdowns, popovers
6px md — card sub-sections
4px sm — pills, small buttons

The design doc says 8/4; the code also uses 6px (separate, bind-rows, pivot-longer, unite) plus stray 2px/12px/999px in dock/ui. Decision needed: bless the 6px tier (recommended, it's in real use) and eliminate the strays.

3.5 Boolean controls: toggle pills — there are no checkboxes consolidate

The JS-driven system deliberately has no native checkboxes, radio buttons, or switches. Every boolean or small-enum choice is a click-through toggle pill (.blockr-pill, 24px) — either cycling (operator =/>/<), binary (AND/OR, asc/desc, n/%), or self-labeling on/off (popover options). Active state = primary color + 8% primary tint + 20-30% primary border.

The worst duplication in the system lives here. The pill "active" recipe (color: primary; background: rgba(37,99,235,0.08); border-color: rgba(37,99,235,0.2)) is re-implemented with !important in at least five places: .sb-toggle-active (select-block.css:23), .fb-preserve-active (filter-block.css:37), .ab-dir-desc (arrange-block.css:22), .slb-mode-active (slice-block.css:32), .blockr-popover-toggle-active (blockr-blocks.css:308). The checkbox/switch decision is made (§5.4): values → pill, data options → checkbox, UI modes → switch — .blockr-checkbox is shipped in blockr.viz and every self-labeling on/off pill listed above migrates to it with the shared layer (live designs + rule in boolean-controls-proposals.html).

5.2 The token contract

The :root block at the top of this file is the proposal: dock's existing tokens minus the two dead greys (600/800 fold into 700/900 — see §2.1), plus 11 additions (--blockr-color-danger, --blockr-font-mono, 3 radius tiers, --blockr-shadow-dropdown, --blockr-focus-ring, 3 control heights — see §2.5, --blockr-transition). Rules:

  • Components reference semantic tokens (--blockr-color-*), never primitives, never literals. Primitives (--blockr-grey-*, --blockr-blue-*) exist only to feed the semantic layer. This keeps dark mode a one-file option later.
  • Fallbacks stay in consuming CSS (var(--blockr-x, #literal)) so a lone block renders sensibly without the token sheet — but fallback values must equal token values (a lintable invariant).
  • Data-encoding colors never become UI tokens. Chart palettes/ramps stay in blockr.theme; the Okabe-Ito category palette ships as R data (blk_color()) with CSS tints derived where needed.

5.3 Naming rules for classes depending packages use

  1. Namespace: everything blockr.ui ships is .blockr-*. The prefix is reserved — block packages use their short prefixes (fb-, mb-, …) and never mint blockr- classes.
  2. Components are BEM: .blockr-<component>, elements __el, modifiers --mod — the convention blockr.docs already documents and Select/Input already follow. Flat-chain components migrate at move time: e.g. .blockr-row-remove → .blockr-row__remove, .blockr-block-browser-card-name → .blockr-block-browser__card-name, .blockr-sidebar-header → .blockr-sidebar__header.
  3. Utility/typography classes stay flat: .blockr-title, .blockr-label, .blockr-helper, .blockr-meta, .blockr-error — they are single-purpose text styles, not components.
  4. State via modifiers, not sibling classes: .blockr-sidebar--open rather than .blockr-sidebar-open. In particular one shared .blockr-pill--active replaces the five per-block *-active re-implementations; block CSS never restyles shared classes with !important.
  5. Renames are low-risk because markup is generated by exported R/JS builders — consumers call block_browser_ui(), they don't hand-write the classes. During a transition window builders emit both old and new class names on the same elements; old names drop after one release cycle. The exception to audit: packages layering delta CSS onto blockr.ui classes (e.g. blockr.viz on table-preview via table_preview_css()).

5.5 Keystroke labels — one glyph, one rule

Two shipped precedents already agree: the mutate confirm button ("Enter ↵", blockr.dplyr/inst/js/mutate-block.js:170) and blockr.extra's code-editor Run button ("Run ↵" with a muted glyph + full shortcut in the tooltip: title="Run (⌘/Ctrl + Enter)", blockr.extra/R/code-editor.R:257-266, code-block.css:144). Formalized:

RuleDetail
The Enter glyph is ↵ (U+21B5)Most widely used software glyph (Microsoft keycaps), renders reliably across fonts. Rejected: ⏎ U+23CE (the ISO keycap symbol — rendering varies badly by typeface) and ↩ U+21A9 (Apple-specific Return; Apple even distinguishes Return ↩ from Enter ⌅ — a distinction our users don't need).
In controls: verb + muted glyph; compact: glyph onlyRoom available → Enter ↵ / Run ↵ (glyph at ~55% opacity, 0.95em — the blockr.extra recipe, proposed class .blockr-kbd). Tight inline contexts → a bare ↵ chip. Never smaller than the 26px hit area.
Confirm chips cycle: armed → ✓Dirty value → the chip shows the keystroke (Enter ↵, primary-tinted, clickable). Committing (key or click) → the chip's content is replaced by the ✓ icon, faded (.confirmed) — the keystroke hint disappears because there is nothing left to do. Typing re-arms it. This is the shipped mutate behavior (mutate-block.js:182-200, swaps in Blockr.icons.confirm); every future confirm chip follows it.
Always spell it in the tooltipThe glyph alone is not self-evident to every user (NN/g: associate symbols with key names). Every glyph carries title with the spelled shortcut — that's what licenses the compact form.
Modifiers: spell, don't symbolA web app can't assume the OS. Static text uses the dual form "⌘/Ctrl + Enter" (blockr.extra precedent); JS-rendered labels may platform-switch (⌘ on mac, Ctrl elsewhere). Bare macOS symbol strings (⇧⌘K) only if platform-detected — never as static text.
In prose & docs: <kbd>Spelled key names, "+" separators: press Shift+Enter.

Applied to the text-commit decision (text-commit-proposals.html, now decided: the Enter-affordance confirm): the confirm chip shows Enter ↵ where space allows and degrades to a bare ↵ chip inline — both with title="Apply (Enter)".

5.6 What deliberately stays out of blockr.ui

  • blockr.dock: .dv-* overrides, .blockr-view-* stacking/nav, empty-dock prompt, ext-edit, the bslib shade tuning.
  • Block packages: the 13 per-block stylesheets and any block-specific layout.
  • blockr.theme: scale maps, chart palettes, ramps (data colors).
  • blockr.core: stays CSS-free.
  • cynkra brand: marketing identity; the product system remains brand-neutral.
