Outline — starting a new section

Chapter management now has merge-up, ungroup, bulk report toggle and drag-a-block-into-a-chapter. The missing half is creating one. A section is a contiguous run of the document, so "new section" always means the same thing underneath — a boundary is introduced at a point, and everything from there to the next boundary becomes the new chapter — the open question is which gesture expresses it.

Not blocked after all. The earlier attempt failed because the payload was malformed (stacks(list(...)) instead of do.call(stacks, ...)), not because extensions cannot create stacks: the dock's own add_stack_action commits update(list(stacks = list(add = ...))) the same way. Every proposal below is buildable.

A — split at the boundary recommended

A dashed "split here" pill on the gap between two sections, revealed while the outline is hovered. The blocks below the cut become a new chapter, up to the next existing boundary. It is the exact inverse of merge up (which removes a boundary), so the two read as one pair; and it reuses the boundary geometry already established by the insert and reorder rounds.

B — "New chapter" on the block

A text link beside "Add block" in the block's hover row: this block starts a chapter. Same operation, anchored to a block rather than a gap. Slightly more explicit about what moves ("from here down"), and it needs no new geometry — but it crowds the add row, and the boundary, not the block, is where a reader's eye goes when thinking "the next section starts here".

C — drag into the gap later

Dropping a chip on a chapter heading already moves it into that chapter. The symmetric gesture: dropping it on the gap between chapters creates a new one containing just that block. No new affordance at all — the drag already exists — but it is invisible until discovered, and it only ever makes single-block chapters. Good as an accelerator once A or B teaches the concept.

D — toolbar "+ Chapter" rejected

An explicit button that adds an empty chapter to fill later. Familiar from slide tools, but an empty stack is a strange object in this model (chapters are runs of blocks, not containers), it has no obvious position in a dependency-ordered document, and the user is then obliged to drag blocks into it. Rejected unless empty stacks become meaningful elsewhere.

E — select a range, then group later

Shift-click two chips to select a run, then "group into chapter". The most direct expression of "these blocks belong together", and the only one that can create a chapter in the middle without splitting twice. Cost: a selection model the outline does not have, plus selection styling on chips. Worth revisiting if authors start reorganising large boards.

Shared details, whichever wins

  • Naming: a new chapter is created as "New chapter" with its title immediately in inline-rename mode (auto-focused, Enter commits) — one gesture, not create-then-rename.
  • Colour: take the next suggestion from suggest_new_colors() so the thread reads as a distinct chapter at once.
  • Atomicity: the detach from the old stack and the new stack must ride in ONE update payload (mod/rm + add together) — a block may sit in at most one stack, and the halves do not compose across flushes.
  • Where splitting is impossible: none — a split is always legal, since it only partitions the existing order. (Unlike reordering, which the DAG can forbid.)

Recommendation: A, with C as a free accelerator later. The boundary pill is where the reader already thinks about section breaks, it pairs exactly with merge-up, and the outline already renders boundaries. B is a fine substitute if you would rather keep every action in the block's hover row and leave gaps untouched — the underlying operation is identical, so the choice is purely about where the hand goes.
