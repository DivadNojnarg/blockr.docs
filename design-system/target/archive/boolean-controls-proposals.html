Boolean controls: checkbox, switch, or pill?

Companion to design-system.html (§3.5, drift #14/#15). Finding: the system has no checkboxes or switches — every boolean is a click-through pill, including plain on/off options where a pill hides its own state semantics. This document proposes real .blockr-checkbox and .blockr-switch components (all demos below are live — click them) and, more importantly, the rule for which control means what, so all three can coexist without ambiguity.

The diagnosis: pills are excellent when the label is the value (AND/OR, asc/desc, n/%) or when space is the binding constraint — and overused everywhere else. A self-labeling on/off pill ("drop NA") has a readability flaw: an inactive pill and an active pill both just say "drop NA"; the state lives only in a subtle tint. A checkbox says the same thing with an unambiguous state indicator that every user already knows how to read.

1 — The decision rule proposal

One sentence per control, chosen by what the label is, not by taste:

ControlThe label is…Use forExamples
Pill (cycling / segmented) …the value itself of a small enum 2–4 short data-like values you flip between; also the escape hatch when inline space is the binding constraint (inside a 42px row) AND / OR · asc / desc · n / % · operator is/>/≤
Checkbox …a description of an option you include or not On/off data options, especially lists of independent booleans in the settings band — the default boolean control drop NA · names repair · sort · remove input cols · na_rm · preserve order
Switch …a mode of the surface itself Chrome/UI-level state with an immediately visible behavioral flip; at most one or two per surface, never in option lists live preview on/off · lock block · show issues · edit mode

Shorthand: values → pill, data options → checkbox, UI modes → switch. The pattern that dies: the self-labeling on/off pill (.blockr-popover-toggle-active, .sb-toggle-active, .fb-preserve-active, unite's toggles) deprecate — every one of those is a data option, i.e. a checkbox.

2 — The proposed components (live)

.blockr-checkbox — 16px box, radius-sm, primary when checked, 13px label, 26px hit area

State is structural (box fills), not a tint on the label. Native <input> under the hood: keyboard, forms, a11y for free. Uses only existing tokens — radius-sm, primary, grey-300/400, focus ring, control-h-xs, transition.

.blockr-switch — 30×18 track, 14px knob, primary when on. Reserved for modes

Visually heavier than a checkbox on purpose — it signals "this flips how the surface behaves right now". Scarcity is part of the design: if a panel needs five switches, they were checkboxes. Also the natural restyle target for bslib's input_switch (block card header) — closing drift #15.

4 — Where pills remain correct (and where the checkbox goes inline)

Pills keep the enum jobs. The filter footer shows both worlds coexisting under the rule — the AND/OR value pill stays, the "preserve order" option becomes a checkbox:

Note the AND/OR pill and the operator pill read naturally as values you flip; the checkbox reads as an option you include. The mixed footer is less ambiguous than today's all-pill version, because the two visual languages now carry different meanings. Where a checkbox genuinely doesn't fit inline (a cramped 42px row), the rule's escape hatch applies — a pill is acceptable when space is the binding constraint — but that should be the documented exception, not the default.

Both components ship in blockr.ui next to Select/Input: blockr-forms.css + tiny factories in blockr-core.js (Blockr.checkbox(label, checked, onChange) / Blockr.toggleSwitch(…)), plus a .form-check/.form-switch override section in blockr-base.css so the Bootstrap side matches without R code changes. Everything above uses only existing tokens — no new primitive values were introduced (16px box and 30×18 track are component internals, like the Select tag's 16px remove button).

Recommendation: adopt both, with the rule from §1 written into the design system: values → pill, data options → checkbox, UI modes → switch. In practice that makes the checkbox the workhorse (it replaces every self-labeling on/off pill), keeps pills exactly where they shine (enums + tight inline spots), and holds the switch in reserve for the few chrome-level modes — its rarity is what keeps it meaningful. If only one new control is adopted, make it the checkbox; the switch can follow when a real mode-toggle use case lands in blockr.ui chrome.
