Text fields: when does typing become the pipeline's truth?

Companion #4 to design-system.html. Expression editors (Blockr.Input) commit on explicit confirm — that's settled: half-typed code is a parse error. The open decision is plain free-text fields (rename's new name, mutate's column name, unite/separate names, the gear band's prefixes and labels). Today they auto-submit per keystroke (300ms debounce). Type in each demo below — the red counter is a mock "downstream pipeline" that recomputes on every commit, so you can feel the difference. The demo row is the rename block: bill_len → ….

A — Today: 300ms debounce per keystroke status quo

Every pause >300ms while typing commits the value and recomputes everything downstream. Type body_mass_corrected at normal speed and watch the counter: each burst of typing costs a recompute, and downstream sees the half-typed names (body_ma…).

Feel: zero friction, but the pipeline churns while you think. On a large board each of those recomputes is a real dplyr cascade + re-render — and downstream blocks referencing the final name break-then-heal mid-typing.

B — Commit on blur or Enter recommended

No new chrome at all — the row looks identical to A. The only change is when the value ships: when you press Enter or click/tab away from the field (blur). While the field still has focus, nothing fires. Type the same name, then hit Enter (or click anywhere outside): exactly one recompute, with the final name.

Feel: "done typing → applies". The interaction grammar is the one every spreadsheet and form uses, so nobody has to learn it. The one caveat: while the field has focus there is no visual signal that the shown value isn't applied yet — you type, glance at the output, and it hasn't moved. The demo includes the cheap mitigation: a small blue pending dot that appears while the value is edited-but-uncommitted and disappears on commit. That dot is the entire extra UI; it is optional.

C — Explicit confirm button (the expression pattern, extended)

Same commit timing as B (nothing fires while you type) plus a button: the mutate-style "Enter ↵" appears armed while the value is dirty; clicking it (or pressing Enter) commits, then it collapses to a faded ✓. Blur does not commit — the button is the contract. Type and watch the button arm; commit and watch it confirm.

rename block — type, then click "Enter ↵" (or press Enter)

Feel: maximally explicit — the dirty state is always visible and nothing ever ships without your say-so. The costs: one more button on every text row (the rename block would carry one per rename), one more required click for the mouse-driven user, and it dilutes the design-system meaning of "Enter ↵", which today signals code being applied — a strong affordance worth reserving.

So what is actually different between B and C?

They share the important half: neither commits per keystroke. They differ only in the contract for the final commit:

DECIDED (2026-07-02): B and C share the commit timing; the meaningful difference is the affordance — and showing the key teaches the gesture. So plain text fields get B's timing wearing C's Enter cue: nothing commits per keystroke; Enter commits; blur also commits (B's safety net — C's forget-to-commit failure mode disappears); while dirty, the field shows the Enter chip instead of the anonymous pending dot. The chip follows the keystroke-label rules (design-system.html §5.5):

room available: verb + muted ↵ glyph compact inline: bare ↵ chip — licensed by the spelled-out title tooltip

The glyph is ↵ (U+21B5) everywhere — the established house glyph (mutate's "Enter ↵", blockr.extra's "Run ↵" + title="Run (⌘/Ctrl + Enter)"), the most robust cross-font rendering (⏎ U+23CE, the ISO keycap symbol, varies by typeface — it even fails to render in some system fonts; ↩ U+21A9 is Apple's Return). Expression editors keep their confirm as-is — same visual family, so the two commit models now read identically. Implementation pending; the current debounce (A) still ships until the blocks are migrated.
