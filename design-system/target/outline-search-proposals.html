Outline search — one box over the whole board

The outline lists the report. Everything else on the board, which on a CDEx-sized board is 90 % of it, has to be reachable by search. Today that is split over two controls, neither of which sees the whole board. These are three ways to make it one.

What changed underneath. The outline no longer lists every block, only the ones flagged for the report, and the report flag now defaults to off. A fresh board opens on an empty document. That makes the search box the primary way blocks enter the document, not a convenience.

Today what we are replacing

Two controls, 150 px and 280 px wide, at opposite ends of the panel. The top one filters the rows that are already listed. The bottom one adds from the pool. Neither searches the other's set, and on a real dock panel (375 px measured on the 80-block demo) the picker is squeezed to 161 px.

A. One command bar recommended

One full-width box under the report title. Focus opens it on the whole board, typing narrows it. Results come back in two groups, what is already in the report and what is not, so the same query answers both "where is that block" and "give me that block". Clicking an entry in the first group scrolls to its row; clicking one in the second adds it to the report. The menu stays open after an add, so building a document is: type, Enter, type, Enter.

What each result row carries

PartWhy it is there
Icon tileThe block's own icon, the same one the outline row and the dock tab show. Cheap recognition, already rendered per class.
NameThe block name, with the matched substring marked.
Meta lineChapter, block type, and the first words of the description. On a pharma board the description is what distinguishes "Table 14.3.1" from "Table 14.3.2".
runs pillThe block is not in the report but the report depends on it, so it already runs invisibly (include=FALSE). Adding it only makes its output visible.
Trailing actionAdd for the pool, Go to for what is already listed. The action is a word, not an icon: the two groups do different things and the row should say which.

B. Filter in place, offer the pool alternative

Same box, but the two answers land in different places: matching rows that are already in the report stay in the document and everything else is hidden (today's client-side filter), while the dropdown carries only the blocks that are not in the report. You see in-report matches as real rows, with their descriptions and code, rather than as one-line summaries.

The cost is that one box has two visual outputs and the document jumps around while typing. That was worth it when the outline listed all 80 blocks. Now that it lists only the report, typically a handful of rows, filtering it buys little.

C. Results in flow, no overlay alternative

Identical control and identical grouping, except the results are not a popup: they render in the panel, pushing the document down, and stay until the query is cleared. Nothing is hidden behind a layer, which matters in a dock panel that can be 375 px wide, and the result list can breathe (two lines per entry).

The cost is that the document is pushed out of view exactly when you are trying to decide what it still needs, and the panel scroll position moves under you.

Built A, on the block browser's rows, blockr.outline 0.0.82

The shipped control is variant A wearing the block browser's clothes. The mocks below predate that decision and keep their own row styling; treat them as the record of the behaviour (two groups, go-to versus add, menu stays open after an add), not of the visual detail.

What that means concretely: the field is .blockr-block-browser-search (magnifier, grey-50 fill, blue focus ring, native clear), the rows are .blockr-block-browser-card with the 32 px tinted icon tile and the 14 px name, the sections are .blockr-block-browser-category headers, and keyboard selection uses the browser's own .card-selected, with wrapping arrows and the top hit selected after every keystroke so Enter always does something. Two divergences on purpose: the second line is the block description rather than the package name, because on a report board that is what tells two similar tables apart, and the package pill slot carries the runs marker instead.

Two traps for anyone reusing those classes elsewhere. The --bb-* tokens the card CSS reads are declared on the browser's own roots, so a third consumer has to provide them; blockr.outline maps them onto the --blockr-* scale rather than copying the values. And wearing .blockr-block-browser itself to get those tokens is a trap: that class is also the browser's Shiny input binding and search JS, which promptly adopted the outline's control as a browser instance, filtered it by data attributes these cards do not carry and declared it empty.

Recommendation

Variant A. One box, one popup, two groups. It is the only one of the three where the same keystroke sequence works whether or not the block happens to be in the report already, and it leaves the document alone while you search, which is what you want when the question is "what is missing from this deck".

C is the fallback if the overlay turns out to sit badly in a narrow dock panel; it is the same component with position: static on the menu, so the decision can be deferred and flipped with one class.
